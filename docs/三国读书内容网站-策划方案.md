# 三国读书内容网站｜完整策划方案

版本：v0.1（2026-11-13）
对标参考：小红书笔记《我用 AI，给娃造了个能"走进去"的三国世界》，作者「十月妈妈会发光」，其作品名为「三国图志」
文档性质：规划稿，不含代码实现；确认后可直接作为开发任务书与内容生产规格书使用。

---

## 0. 产品定义与边界

**一句话定义**：把《三国演义》120 回拆成故事、人物、地理、时间、原文五条可互相跳转的线索，让"读完记不住人名地名"变成"顺着一条线索一直读下去"。

**核心洞察（来自对标笔记）**：读三国的困难不在故事，而在三件事——人物太多且阵营会变、地名与行政区划随时代变化、小说与正史混在一起。五个入口各自解决其中一个困惑，因此功能看起来多，逻辑其实单一。

**本方案与对标笔记的取舍**：

| 项目 | 对标笔记 | 本方案 |
| --- | --- | --- |
| 人物规模 | 1235 人全量星图 | P0 只做 60 人（核心人物 + 每回出场者），做出处与关系，不追求数量 |
| 插画 | 120 张回目插画 | 保留一回一图，但先用统一提示词模板 + 分批生成，允许占位图 |
| 对话 | 演示性质，强调"207 年的诸葛亮不知道赤壁结局" | 升级为可工程化的「年份知识边界」，且不依赖大模型即可实现（见 4.5、7.5） |
| 出处 | 小说 / 正史 / 后世传说分开标注 | 提升为全站第一原则，做成数据字段与视觉标签，而不是说明文字 |
| 目标人群 | 亲子启蒙为主 | 亲子共读为主入口，成人可沿同一条动线深挖，不另做一套内容 |

**明确不做的（防止范围失控）**：不做社区/评论、不做用户账号体系、不做付费、不做 1235 人全量人物库、不做精确历史 GIS 复原、不在 P0 阶段引入大模型对话。

## 1. 用户与场景

| 用户 | 典型场景 | 真实需求 | 承接模块 |
| --- | --- | --- | --- |
| 家长 + 8–14 岁孩子（主） | 睡前讲三国、读完一段想追问"这人是谁" | 白话、有画面、能一句话讲清、不吓人不血腥 | 故事馆、插画、人物卡"一句话定位" |
| 成人自学者 / 三国爱好者 | 读到某回想查人物关系、想分清哪些是史实 | 出处可查、关系可展开、原文可跳转 | 典籍室、人物关系、史料对照 |
| 老师 / 内容创作者 | 备课、做读书卡片、找一张能说明局势的图 | 可引用、可导出、标注清晰 | 事件专题、地图年表、卡片视图 |

**分级原则**：不分成"儿童版/成人版"两套内容，只在同一条目上分层展示——默认层是白话导读与插画，展开层是原文、关系与史料。用户自己决定读多深。

---

## 2. 内容三原则（全站最高约束）

1. **出处三分法**：每一条内容必须打且只打一个来源标签——`演义`（小说）、`正史`（《三国志》及裴注等）、`传说`（民间、戏曲、后世演绎）。三种标签在 UI 上用固定颜色与文字标识，不得混用、不得省略。这是本网站相对同类产品最硬的可信度资产。
2. **同一条动线**：插画 → 回目 → 人物 → 地理/年表 → 原文回目 → 史料出处。任何页面都必须能"往上走一步、往下走一步"，不允许死胡同。
3. **时间优先**：人物、事件、势力、地理信息一律带年份上下文。人物的阵营、官职、所在地随年份变化，用区间表示，不写成固定属性。对标笔记里"207 年的诸葛亮不知道赤壁结局"就是这条原则的产品化表达。

## 3. 信息架构

```
首页 /                     三条起手路径：从故事 / 从人物 / 从地图，外加「今日一回」
├── 故事馆 /chapters       120 回索引（按回目 / 年份 / 关键事件筛选）
│   ├── 回目详情 /chapters/:id
│   └── 事件专题 /events/:id        赤壁等大战：前因 / 经过 / 后果 / 多视角切换
├── 人物馆 /people         列表 + 阵营/时期/身份筛选
│   ├── 人物详情 /people/:id
│   └── 关系图 /people/:id/relations
├── 山河 · 年表 /map       时间轴 + 地理绘卷 + 人物足迹叠加
├── 对话台 /dialogue       选定人物 + 年份的问答（P1）
├── 典籍室 /sources        原文回目、史料条目、三分法说明
│   └── 条目详情 /sources/:id
├── 搜索 /search           全局检索：人名、地名、回目、事件
└── 关于 /about            使用方法、内容规范、底本与版权说明、校勘记录
```

**全局组件**：顶部导航、全局搜索框、出处三分法图例、面包屑、"本条目涉及"侧栏（这一回出现的人 / 这一人出场的回 / 这一年的大事）、阅读进度（本地存储，不上传）。

**标准动线示例**：首页点「今日一回」→ 第四十九回插画与导读 → 点「诸葛亮」→ 人物卡显示建安十三年（208）所属阵营与关系 → 点「借东风」事件 → 时间轴定位 208 年 → 侧栏给出《三国志》相关记载并标注「演义虚构」→ 回到原文回目。

## 5. 内容规范（可直接交给 AI 批量生产的规格）

### 5.1 回目条目（chapters）

| 字段 | 类型 | 必填 | 示例 | 要求 |
| --- | --- | --- | --- | --- |
| `id` | string | 是 | `ch-049` | 三位回目序号，与原文回目一一对应 |
| `title` | string | 是 | 七星坛诸葛祭风 三江口周瑜纵火 | 用底本原有回目，不改写 |
| `era` | string | 是 | 建安十三年 | 东汉年号 |
| `year` | number | 是 | 208 | 公元年；无明确纪年时置空并标注「约」 |
| `summary` | string | 是 | 一句话，≤30 字 | 不出现后文情节 |
| `guide` | string | 是 | 200–250 字白话导读 | 见下方写作规则 |
| `illustration` | string | 是 | `/img/ch049.webp` | 一图一回，含 alt 文本 |
| `people_ids` | string[] | 是 | — | 该回出场人物，关联人物库 |
| `place_ids` | string[] | 否 | — | 关联地名库 |
| `event_ids` | string[] | 否 | — | 关联事件库 |
| `source_type` | enum | 是 | 演义 | 回目主体一律为「演义」 |
| `source_refs` | string[] | 否 | — | 对应原文回目 / 史料条目 ID |
| `question` | string | 是 | 一个开放式问题 | 给孩子，不设标准答案 |
| `review` | enum | 是 | 待校 / 已校 | AI 生成内容初始为「待校」 |

**导读写作八条**：① 白话、短句，每段不超过 3 行；② 先讲"谁想干什么"，再讲"结果如何"；③ 生僻字与多音字首次出现给注音；④ 不下道德结论、不做人物评价；⑤ 不剧透本回之后的情节；⑥ 涉及虚构情节时，句末用标签标注「演义」；⑦ 数字与年份用阿拉伯数字，年号用汉字；⑧ 结尾留一个可追问的点，与 `question` 呼应。

### 5.2 人物条目（people）

固定字段：姓名、字/号、生卒（不详则标「不详」，不许推测）、`一句话定位`（≤25 字）、首次出场回目、身份、`阵营区间`（数组：`{from_year, to_year, faction}`，阵营变化必须分段）、关系列表、出处标签、`review` 状态。

关系类型枚举：`君臣` `亲属` `师友` `同僚` `敌对` `归附` `婚姻`。每条关系带 `since_year` 与 `source_type`，避免把"后来敌对"写成"天生敌对"。

### 5.3 事件与战役（events）

固定字段：名称、起止年份、`phase`（前因 / 经过 / 后果）三段、参与方、`viewpoints`（至少两个人物视角，各 80–120 字，用该人物当时能掌握的信息写）、关联回目、`source_type`、史料对照。

赤壁之战是 P0 的样板条目：必须同时呈现"演义写法"与"正史记载"的并列卡片。

### 5.4 地名与纪年

- 年号与公元年双轨显示，如「建安十二年（207）」；建安二十五年之后注意延康/黄初的改元。
- 古今地名对照一律写「约今……」，只用省级或大区域描述，不标精确坐标，不下"即今某市"的断言。
- 建立统一的古今地名对照表与异体字表（如「雒阳／洛阳」、「彝陵／夷陵」），全站按表统一。

### 5.5 史料与出处（sources）

每条引文：书名、篇目、引文（短引，注明版本/底本）、对应回目、`source_type`、一句话说明"与演义的差异"。**红线**：不得为人物或事件编造史料出处；找不到对应记载时明确写「正史无对应记载」，而不是省略。

### 5.6 插画

- 统一风格：水墨线描 + 淡设色，横向 4:3，主体居中，留出标题安全区。
- 生产规范：固定提示词前缀 + 固定色彩脚本 + 参考图；每条插画在内容库里保存完整提示词与生成参数，便于重绘与风格统一。
- 穿帮检查清单：现代建筑、现代服饰、现代兵器、简体字招牌、明显错误的旗帜字号、透视错误的城墙。
- P0 允许使用占位图，但占位图必须显示「插画待补」，不许用风格不一致的网图凑数。

### 5.7 版权与底本

原著文本属公有领域，但现代整理本的标点、校勘、注释可能另有权利。建议：使用公版古籍影印或明确的公版电子文本作底本，在「关于」页写明底本来源；不整本搬运受版权保护的整理本；史料只作短引并注明出处；插画为 AI 生成并保留生成记录。

## 6. 数据结构与内容工程

### 6.1 存储策略

**起步不建数据库**：全部内容以「Markdown 正文 + YAML front matter」文件形式放在仓库 `content/` 下，构建期生成 `chapters.json / people.json / events.json / places.json / timeline.json / sources.json` 与一份搜索索引。

理由：内容可被人直接阅读校勘、改动有 git diff、AI 可批量生成与批量修订、站点可纯静态部署、零运维成本。当内容量超过约 5000 条或需要用户数据时，再迁到数据库。

```
content/
├── chapters/001.md ... 120.md
├── people/liubei.md ...
├── events/chibi.md ...
├── places/luoyang.md ...
├── timeline/184-220.yaml
├── sources/sanguozhi-*.md
├── illustrations/  (图片 + .prompt.json)
└── schema/         (字段定义与校验规则)
```

### 6.2 实体关系

- `chapters` 多对多 `people` / `places` / `events` / `sources`
- `people` 多对多 `people`（通过 `relations`，带类型与起始年份）
- `events` 属于 `timeline`，包含多个 `viewpoints`
- `places` 带 `modern_hint`（约今，非坐标）
- 所有实体共享 `source_type` 与 `review` 两个字段

### 6.3 条目样例（人物）

```json
{
  "id": "zhugeliang",
  "name": "诸葛亮",
  "zi": "孔明",
  "life": "181–234",
  "tagline": "刘备的谋主，蜀汉的执政者",
  "first_chapter": "ch-037",
  "factions": [
    { "from_year": 207, "to_year": 234, "faction": "刘备集团／蜀汉", "source_type": "演义" }
  ],
  "relations": [
    { "to": "liubei", "type": "君臣", "since_year": 207, "source_type": "正史" }
  ],
  "source_refs": ["sgz-zhugeliang-zhuan"],
  "source_type": "正史",
  "review": "待校"
}
```

### 6.4 构建期校验（必须自动化）

字段完整性、`year` 落在 184–280 范围内且有对应年号、所有 `*_ids` 引用存在、`source_type` 合法且非空、`review=待校` 的条目数量统计、异体字按对照表归一、插画文件存在。校验失败即阻断构建，避免"看起来做完了但一半内容是空的"。

## 7. 技术选型

| 层 | 方案 A（推荐，P0 起步） | 方案 B（有后端，P2 以后） |
| --- | --- | --- |
| 形态 | 纯静态站点，构建后为 HTML/JS/JSON | 静态前端 + 轻量 API |
| 前端 | Vite + React + TypeScript + CSS Modules | 同左 |
| 内容 | 仓库内 MD/YAML → 构建期 JSON | 数据库 + 内容管理后台 |
| 搜索 | 构建期生成索引（MiniSearch / FlexSearch），中文按二元分词 | 服务端全文检索 |
| 关系图 / 星图 | SVG + d3-force；星图用 Canvas 极坐标自绘 | 同左 |
| 地图 | 插画绘卷优先；需真实底图时见 7.6 | 同左 |
| 对话台 | 预设问答 + 年份过滤，不调用大模型 | 后端代理 LLM，密钥只在服务端 |
| 部署 | 静态托管 + CDN + PWA 离线缓存 | 加 API 服务与数据库 |
| 成本 | 近乎为零 | 有服务器与模型调用成本 |

**明确不选**：不做 SSR 框架（内容是静态的，构建期渲染足够）、不上重型 CMS（内容生产靠脚本 + git）、不在前端放任何密钥。

### 7.5 对话台的"年份知识边界"（差异化重点）

不依赖大模型也能做出对标笔记那个最有记忆点的设计：

1. 用户选人物 `P` 与年份 `Y`；
2. 系统从 `events` / `chapters` 中筛出 `year <= Y` 且该人物参与或可推断知晓的条目，构成"此时此人可知的事实集合"；
3. 问答基于该集合回答，界面固定显示「知识截止：建安十二年（207）」；
4. 命中 `year > Y` 的内容一律不返回，并给出一句解释「此事发生在 208 年，此时尚未发生」。

P2 若接入大模型，把该集合作为唯一可选上下文注入系统提示，仍由服务端代理调用，前端不接触密钥。

### 7.6 地图模块合规约束（硬性）

- 底图服务商仅限：腾讯地图（默认）、高德、百度、天地图。**禁止** Google Maps、Apple Maps、Bing 海外版、Mapbox、Leaflet + OpenStreetMap 直连海外瓦片等无资质来源。
- 坐标系使用 GCJ-02；不得自行拼接或绘制现行国界、行政区划边界。
- 默认采用腾讯地图 GL JS 的代理模式，SDK 地址不带 `key`，前端不出现任何可用密钥；用户自备密钥时需自行在对应开放平台申请，并配置域名白名单或服务端代理。
- **P0 推荐做法**：完全不用在线底图，改用「手绘山河绘卷」——一张风格化示意图 + 可叠加的城池点位与人物足迹线。既符合全站插画风格，也彻底规避底图合规问题与密钥问题，且可离线。
- 历史疆域只作示意表达，不标注争议边界；古今地名一律用「约今」；不采集、不存储、不公开任何用户位置数据。

## 8. 内容工程量与生产流水线

| 内容 | P0 数量 | 全量目标 | 备注 |
| --- | --- | --- | --- |
| 回目条目 | 12 回（含赤壁相关回） | 120 回 | 每回约 250 字正文 + 元数据 |
| 插画 | 12 张 | 120 张 | 一图一回，统一提示词 |
| 人物 | 60 人 | 约 150 人 | 不追 1235 人全量 |
| 事件专题 | 3 个（黄巾、官渡、赤壁） | 约 20 个 | 每个含多视角 |
| 年表条目 | 20 条 | 约 80 条 | 184–280 关键节点 |
| 史料条目 | 15 条 | 约 100 条 | 与演义差异对照 |

全量约 3 万字正文 + 120 张图 + 数百条关系标注，属于"看起来不大、实际最容易烂尾"的工程，因此必须先跑通流水线再扩量：

**模板定义 → AI 批量生成 → 自动校验（见 6.4）→ 人工抽检 20% → 打「已校」标记 → 入库 → 构建预览**。所有 AI 生成条目初始状态为「待校」，界面可对「待校」内容做弱提示（不隐藏，避免进度假象）。

**质量红线**：不得把演义情节写成正史；不得编造史料出处；不得给人物填写推测性生卒；不得让 `Y` 年之后的事件出现在该年份的对话或视角里。

## 10. 内容运营（学习小红书的部分）

**笔记结构模板**（复用原帖验证过的六段式）：带娃/自用痛点 → 点出认知难点 → 亮出作品名 → 逐条介绍模块（每条「功能 + 解决什么」）→ 讲一个设计理念 → 评论区投票收尾并预告下期。

**连载选题池**（对应原帖「下期细讲」的钩子）：① 120 张回目插画怎么保持风格统一；② 人物星球怎么做出来的；③ 地图与年表怎么把故事放回山河；④ 为什么 207 年的诸葛亮不能知道赤壁；⑤ 小说、正史、传说三分法怎么落地；⑥ 一个人 + AI 怎么搭完整站；⑦ 120 回内容批量生产流水线；⑧ 给孩子讲三国，哪些该讲哪些先不讲。

**执行约定**：标题用「我做了什么 + 一个反常识细节」；封面用站点真实截图而非抽象插画；每篇只讲透一个模块；标签池按"名著/亲子/AI 建站/历史启蒙"四组各取 1–2 个，不堆砌。网站「关于」页与笔记互相导流，笔记里提到的具体回目在站内可被搜索直达。

**可见性**：静态 HTML + 每回独立 URL + 结构化数据（标题、简介、插画），便于搜索引擎与生成式引擎引用；「典籍室」的出处标注是天然的被引用资产。

## 附录 B｜「群英星图」视觉与交互拆解（来自视频截图）

素材：`docs/assets/群英星图-视频截图参考.png`（用户提供的视频单帧截图，2026-11-13）。以下以静态帧可见内容为准，个别小字可能存在辨识误差；动效相关部分标注为推测。

### B.1 画面逐层拆解

| 层级 | 元素 | 做法 | 可复用点 |
| --- | --- | --- | --- |
| 章节标识 | 左上朱红方印「伍」+「人物馆」，右侧金色短实线与灰白虚线 | 把功能包装成古籍卷次 | 比普通导航栏更有调性，且与「典籍室」气质一致 |

| 数据注脚 | 黑底金边胶囊「217 条关系 · 正史 58 · 小说 159」 | 细分数据兜住可信度 | 见 B.2 |
| 数据强调 | 底部金色大字「217 条关系」 | 收尾重复核心数字 | 与顶部「1235 位」形成首尾呼应 |

球面可辨认的人名包括诸葛亮、刘备、孙权、周瑜、徐庶、赵云、张飞、关羽、司马懿、张郃、孟达等。

**配色**：近黑墨蓝底 + 金色（约 #C9A96A 一类）+ 朱红印章 + 青白光晕。**字体**：数字用宋体/衬线，文案用黑体/无衬线。**版式逻辑**：章节编号 → 大数字 → 一句诗性文案 → 主视觉 → 数据注脚 → 数据强调，即「先震撼、再画面、最后给可验证的细分数据」。

### B.2 最值得抄的一点

「正史 58 · 小说 159」把**出处分治做进了视觉层**，而不只是写在说明里。这与本方案第 2 节的三分法完全一致，等于给了一个视觉证据。我们应再往前一步：把这三个数字做成**可点击图例** —— 点「正史」只保留正史关系边，点「传说」只看后世演绎，让筛选本身成为一种阅读方式。

### B.3 工程实现（"会转的星球"）

| 要素 | 实现 | 注意 |
| --- | --- | --- |
| 球面点位 | 每人物一组 (经度, 纬度)，正交投影到 2D；z 深度决定透明度、字号、是否绘制标签 | 1235 点必须用 Canvas，不能用 DOM |
| 自转 | `requestAnimationFrame` 匀速增加全局经度 | 移动端降帧减速；页面不可见时暂停 |
| 点击置中（推测） | 以目标点经纬度为相机目标，缓动插值转到正面中心，高亮其关系边并展开人物卡 | 截图里「诸葛亮在正中」即此状态 |
| 关系边 | 从中心点向邻居画细线；按 `source_type` 用实线/虚线与两种金色区分，按关系类型用线宽区分 | 背面边淡出，避免线条糊成一团 |
| 标签 | 只绘制正面半球可见且优先级高的约 30 个名字，其余悬停显示 | 密集标签是这类图最常见的翻车点 |
| 数据 | 节点来自 `people`，边来自 `relations`（带 `type` / `since_year` / `source_type`），底部统计构建期算好 | 不在运行时遍历全量 |
| 兜底 | 无 Canvas 时退化为静态 SVG 星图 + 可访问的人物列表 | 内容可读性优先于效果 |

### B.4 我们的差异化（不照搬）

1. **不做 1235 人的密集星球**：P0 只有 60–150 人，改做「疏朗星图」，关系可读比气势重要。
2. **加时间轴联动**：拖动年份，只显示该年活跃人物，`since_year` 之前的边不出现，阵营变化用节点外圈颜色变化表达。这是截图里没有的，且能与「207 年的诸葛亮不知道赤壁」串成同一条设计原则。

4. 保留墨蓝 + 金的材质感，但换编号体系、字体与版式细节；截图仅作设计语言参考，不复制其具体视觉资产与文案。
